
	   


Google announced the launch of a new feature designed to block websites from manipulating their visitors' history to make it harder for them to go back to the source page with the help of the browser back button.

This is introduced as part of an effort to eliminate annoyances and abusive website behavior, and to improve overall Chrome user experience.

As explained in a GitHub issue reporting this problem from June 2016, on websites which manipulate their users' web history the process of getting back to one of the previously visited websites is quite hard:

Because of the instant fast-fowarding nature of the dummy history entries, the user can't wait for a visual confirmation to know when to stop hitting the back button.
	As a result, the user either overshoot or undershoot its destination resulting in guaranteed frustration.


To do this, misbehaving websites would add "a history entry using pushState or navigates the user to another page (c.com) without ever getting a user gesture" as described in the new History Manipulation Intervention feature announcement.

Afterward, when the user tries to go back, some of the entries in the history will be automatically skipped thus making it harder to go straight to the target page.

As detailed in the Chromium Issue 907167, the feature will automatically skip all history entries in the "back/forward list on back button invocation" added by websites without visitors' intention.

More to the point, the entries which will be skipped are those added by websites and "actually redirect the user to another URL automatically (with no user gesture ever)."

As the Chrome team reveals, Google's web browser "already replaces entries of pages that do this behavior before load and this intervention strengthens that further by intervening on pages after load as well."

The History Manipulation Intervention announcement also explains to developers the behavior of the new feature:


[..] developers should be aware that if they want the browser’s back button to land on a page that redirected after loading, then that page should have had a user gesture before redirecting. Developers should also be aware that if a history entry is added but there is no user gesture by the time the user hits back, the page adding the history entry will be skipped and the popstate event will not fire.


Google Chrome History Manipulation Intervention is already reviewed and is approved for launch, with the announcement being published to make sure that developers are also aware of this change prior to its official release.

The feature will be available on all six Blink platforms (Windows, Mac, Linux, Chrome OS, Android, and Android WebView), with the intervention only impacting the back and forward buttons and not the history.back/forward API.
