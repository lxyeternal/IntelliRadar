Public input on the new Digital Identity Guideline ended last week, and currently, NIST is working on the official edition, that will be released later this year.

The current draft of the NIST Digital Identity Guideline reveals some of the changes coming next year. These recommendations are important, as they are widely accepted and followed by most government agencies and enterprises around the US, and even around the globe.

Here are the current NIST password policy recommendations included in the latest draft.

› Passwords should be at least 8 characters in length
› Organizations should allow passwords to be up to 64 characters or more in length
› All ASCII or Unicode characters (RFC 20) should be allowed in passwords (including SPACE)
› Organizations may remove one or multiple SPACE characters before verification provided that the result is at least 8 characters in length
› Organizations should not truncate passwords
› Organizations that generate initial user passwords should use an approved random bit generator. These passwords must be at least six characters in length
› Password hints should never be accessible to unauthenticated users
› Organizations should not urge or prompt users to use certain types of info for passwords ("What is name of your first pet?")
› When setting up or changing an existing password, organizations can compare the user's new password against passwords obtained from previous breach corpuses, dictionary words, repetitive or sequential characters, or context specific words (usernames, names, derivatives)
› Organizations shall implement a system that limits the number of failed login attempts
› Organizations should not use composition rules (mixtures of different character types)
› Organizations should not require users to change passwords at regular intervals
› Organizations should change passwords only if there's evidence of compromise, or the user initiates it
› Organizations may display the most recent password character for a short period of time, to assist users when entering passwords
› Organizations shall use "approved encryption" to protect passwords
› Organizations shall use an authenticated channel (HTTPS) when requesting passwords
› Organizations shall store memorized secrets in a form that is resistant to offline attacks
› Passwords shall be hashed with a salt value using an approved hash function such as PBKDF2 as described in [SP 800-132]
› The salt value SHALL be a 32-bit or longer random value generated by an approved random bit generator and stored along with the hash result
› At least 10,000 iterations of the hash function should be performed
› A keyed hash function (e.g., HMAC [FIPS198-1]), with the key stored separately from the hashed authenticators (e.g., in a hardware security module) should be used to further resist dictionary attacks against the stored hashed authenticators

The changes in NIST's recent guideline show a relaxation of recommended password policies. This relaxation comes after several studies have shown that users tend to use simpler passwords the more complex password rules become.

The new NIST framework also advises companies to move to multi-factor authentication schemes for a more secure experience. These are user authentication systems that employ multiple user inputs, such as passwords, biometrics data, offline tokens, or SMS messages.
