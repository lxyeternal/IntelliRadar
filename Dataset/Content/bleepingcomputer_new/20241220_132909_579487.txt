In an intent to ship and implement, Chrome developer Mike West has stated that they will be limiting the HTTP Referer header to only 4KiB in order to block attacks, including ones that that could allow sites to determine if you have ever visited a particular page.

As noted in https://github.com/xsleaks/xsleaks/wiki/Browser-Side-Channels#cache-and-error-events, servers will often behave in unexpected ways when presented with an overly-long `Referer` header. This is unfortunate, as `Referer` is one header whose length attackers generally retain control over when generating `no-cors` requests.

In a Google Chrome test conducted by West, this change caused errors in 1 in 10,000 requests. Furthermore, tests that stripped 4KiB and 2KiB referer header limits to the origin did not show any "statistically relevant difference in error rates".

There's some risk to altering the `referer` header, as sites do use it in various ways. This risk seems manageable. Based on Chrome's telemetry from Canary/Dev, the header is rarely long enough to be affected: capping the length at 4k would affect 1 in 10,000 requests. The percentiles look like:

* 25.00%	27.53
* 50.00%	44.76
* 75.00%	79.71
* 95.00%	263.3
* 99.00%	986.5
* 99.50%	1232
* 99.90%	1956
* 99.99%	4162

Still, there's some risk that dropping path information could have an adverse affect on some site, somewhere. We ran an experiment in Canary/Dev that stripped headers down to an origin at 4k and 2k, but didn't find any statistically relevant difference in error rates for either top-level navigations or subresource requests.

Microsoft Edge's Eric Lawrence and Mozilla's Daniel Veditz and Anne van Kesteren all indicated that they are on board with this change. Lawrence indicated that he would even be fine with testing a 2KiB cap.


Proposing possible lower size limits

As the Referer header can easily be manipulated by attackers and as servers often return errors for long Referers, making this change will eliminate attacks that utilize it.

One of these types of attacks called cache probing is explained below.

Limiting Referer size to prevent cache probing

When visiting a site, if the contents of a page is already stored in the browser's cache due to a previous visit, the browser will use that cached content instead of requesting it again from the site.

So you may be wondering what this has to do with a HTTP Referer header and finding out if a visitor has visited a web page or resource?

As explained in this article, when a browser sends a very long Referer to the header, the browser will return an HTTP error code.

Knowing this, a site or attacker can use JavaScript to open a resource with your browser using a very long Referer header and if an error is returned, it means that the page has never been visited and that the resource was retrieved from the site.

On the other hand, if the page or resource is cached, it will not make a connection to the site and thus no error is returned.


One way to "force" an error when fetching a subresource (unless cached), is by forcing the server to reject the request based on data that isn't part of the cache key. There are several ways to do this, for example:

If the server has a Web Application Firewall, one can trigger a false positive (for example, one could try to force the server to trigger DoS protection by doing many network requests in a short period of time).
	If the server has a limit on the size of an HTTP Request, one can set a very long HTTP Referrer, so that when the URL is requested, the server rejects it.
Since the browser would only issue an HTTP request if there isn't something already in the cache, then one can notice that:

If the image/script/css loads without errors, then that must mean that it comes from the cache.
	Otherwise, it must have come from the network (Note that one can also use timing to figure this out.)


By limiting the HTTP Referer header to 4KiB, the web browser hampers the ability for attackers to use that header to generate errors and thus probe the browser's cache.
