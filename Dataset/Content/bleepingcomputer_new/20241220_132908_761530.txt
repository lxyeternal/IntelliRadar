After the Meltdown and Spectre speculative execution vulnerabilities were disclosed, Google fast-tracked a security feature called Site Isolation so it was enabled for most users in Chrome 67.

When enabled, Site Isolation will cause each web site you visit to be loaded into its own process that is further sandboxed to limit what resources and functions that process can access. By isolating sites in this way, it prevents malicious web sites from exploiting speculative execution vulnerabilities to access data loaded in a different browser tab.

Android gets a slimmed-down Site Isolation

When Chrome 77 for Android was released, Google quietly snuck in Site Isolation to further protect mobile users.

Unlike the desktop implementation, Site Isolation on Android will only protect sites that you login into with a password. This is to reduce resource utilization on mobile devices, which have less memory and CPU processing power than a desktop computer.

"We wanted to ensure that Site Isolation does not adversely affect user experience in a resource-constrained environment like Android," Google stated today in a new blog post.

"This is why, unlike desktop platforms where we isolate all sites, Chrome on Android uses a slimmer form of Site Isolation, protecting fewer sites to keep overhead low. More specifically, Site Isolation is turned on only for high-value sites where users log in with a password."

When Chrome 77 detects a password being entered into a site, it will enable the password-triggered Site Isolation on that site going forward. It also utilizes a crowdsourced list of sites that mobile users are known to frequently enter passwords and enables the feature for these sites.

This feature is currently enabled on 99% of users who are running Android with more than 2GB of memory, with one percent being reserved to monitor the feature and improve performance. Google hopes to add more devices in the future.

For users who want the complete protection of Site Isolation so that it is enabled on every site, they can enable the chrome://flags/#enable-site-per-process flag but should expect Chrome to utilize greater resources on the mobile device.

Google says that they plan on expanding the mobile Site Isolation feature to allow users to specify other sites that they wish the feature to be enabled, even if they do not log in to that site.

Chrome 77 for Desktop get additional protections

Unlike Chrome on Android, Google Chrome has been using Site Isolation for all sites starting in Chrome 67, when it was enabled by default.

With Chrome 77, desktop users get increased protection as Site Isolation now protects users from compromised renderer processes. These processes are in charge of what happens in a tab such as turning HTML, CSS, and JavaScript into a web page and displaying it.

Unfortunately, they are also the target of memory corruption bugs that could lead to an attacker running code in another tab. With this new Site Isolation mitigations, Google prevents this type of malicious activity from occurring.

"For example, suppose an attacker discovered and exploited a memory corruption bug in Chrome's rendering engine, Blink. The bug might allow them to run arbitrary native code within the sandboxed renderer process, no longer constrained by the security checks in Blink. However, Chrome's browser process knows what site the renderer process is dedicated to, so it can restrict which cookies, passwords, and site data the entire process is allowed to receive. This makes it far more difficult for attackers to steal cross-site data."

With Chrome 77 and the addition of renderer process protection, Site Isolation protects users from a variety of threats by restricting access to data used by the Browser.

This includes the following protections, with most of them being added in Chrome 73.



	Authentication: Cookies and stored passwords can only be accessed by processes locked to the corresponding site. This protection was added in Chrome 73.
	
	
	Network data: Site Isolation uses Cross-Origin Read Blocking to filter sensitive resource types (e.g., HTML, XML, Microsoft Office, Open Office, JSON, PDF) from a process, even if that process tries to lie to Chrome's network stack about its origin. Resources labeled with a Cross-Origin-Resource-Policy header are also protected.
	
	
	Stored data and permissions: Renderer processes can only access stored data (e.g., localStorage) or permissions (e.g., microphone) based on the process's site lock. 
	
	
	Cross-origin messaging: Chrome's browser process can verify the source origin of postMessage and BroadcastChannel messages, preventing the renderer process from lying about who sent the message.
	


Google hopes to bring these additional protections to Android at a later date.

In addition to the current protections, in the future, Google aims to further protect CSRF defenses, more types of data, and to migrate existing extension so that they do not have broad cross-site access.

Increased bug bounties for Site Isolation bugs

For a limited time, Google is also increasing bug bounty awards for bugs related to Site Isolation.

In-scope bugs that are eligible for awards include:

Bugs that cause two or more cross-site documents from the web to commit in the same process. i.e. force pre-Site Isolation behavior.
	Bugs that cause cross-site data disclosure, even if the bug assumes a compromised renderer. Examples of data protected by Site Isolation: cookies, saved passwords, localStorage, IndexedDB, HTTP resources covered by CORB or CORP.
