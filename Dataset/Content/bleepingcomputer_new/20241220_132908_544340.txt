PowerShell is a task-based command-line shell and scripting language built on .NET. PowerShell helps system administrators and power-users rapidly automate tasks that manage operating systems (Linux, macOS, and Windows) and processes.


The issue only affects local loopback remoting on endpoints where loopback endpoints are specifically configured to allow access to non-Administrator accounts, something which is by default disabled in Windows 10.

Furthermore, seeing that endpoints on which the default settings are left in place, this problem should only impact a very small percentage of Powershell users.

Issue not present on endpoints with default configurations

The issue will be experienced on machines where the endpoint configurations have been modified for very specific use cases where non-Administrator users require access to local loopback remoting.

Moreover, according to Paul Higinbotham, Senior Software Engineer on Microsoft's PowerShell Team:


The breaking change is not in PowerShell but in a system security fix that restricts process creation between Windows sessions. This fix is preventing WinRM (which PowerShell uses as a remoting transport and host) from successfully creating the remote session host, for this particular scenario. There are no plans to update WinRM.


Higinbotham also states that all connections made using Powershell to the localhost will be successfully created when users have Administrator permissions.

Additionally, SSH remoting with PSCore6 and JEA (Just Enough Administration) sessions are not affected by this very narrowly scoped issue.

As workarounds, Higinbotham recommends always using Administrator credentials when for PowerShell local loopback remoting scenarios, as well as using SSH remoting for PSCore6 instances.
