Breaking Down the npm Supply Chain Attack (September 2025)
Listen
Share
Supply chain attacks have been one of the biggest worries in cybersecurity, and this September, we saw it again, this time targeting npm, one of the world’s most widely used package managers. For day 5 of my 30-day cybersecurity challenge, I researched this incident deeply and shared what I learned.
What Happened

On September 15–16, 2025, security researchers discovered dozens of npm packages had been compromised. One of the early ones was @ctrl/tinycolor, among others.
These malicious versions included a post-install script that would run when someone installed the package. That script was set up to do the following things:

Scan for secrets (like GitHub / NPM tokens, environment variables).
If valid developer credentials are found, they are used to publish new malicious updates to other packages controlled by the same maintainer. In other words, it spreads itself.

Attackers also created public GitHub repositories named “Shai-Hulud” to dump stolen credentials, and added malicious GitHub Actions workflows to exfiltrate secrets from repositories. Sometimes, private repos were made public (-migration suffix was used) to expose more data.
Affected Packages and Versions
Several widely used libraries were impacted during this incident. If your project depends on any of these, check your lockfiles and deployments immediately:

debug@4.4.2
chalk@5.6.1
supports-hyperlinks@4.1.1
chalk-template@1.1.1
slice-ansi@7.1.1
wrap-ansi@9.0.1
has-ansi@6.0.1
strip-ansi@7.1.1
ansi-styles@6.2.2
supports-color@10.2.1
ansi-regex@6.2.1
And several other related dependencies linked to the compromised maintainer account (npmjs.com/~qix).
These malicious versions were live for roughly two hours before clean releases were published.
Why This Attack Is a Big Deal

It’s self-propagating: Once a package is compromised, and the attacker finds more npm tokens or access keys, new malicious versions are published and spread further. That means the risk grows faster than traditional supply chain incidents.
The scale is enormous: over 180 npm packages are compromised across multiple maintainers, and millions of downloads are potentially impacted.
The attack leverages trust: developers, CI/CD pipelines, and open source maintainers often assume packages are safe if they come from npm. This worm shows how those assumptions can be exploited.
Technical Details (How It Worked)

Malicious code (in many cases via bundle.js) is triggered during npm install (post-install script).
It uses tools like TruffleHog to scan for exposed secrets in the local environment.
If GitHub tokens are found, the malware attempts to push GitHub Actions workflows that exfiltrate secrets to attacker-controlled endpoints, make private repos public, or migrate them.
It tries to find npm tokens and then automatically publishes malicious versions of other packages maintained by that user — a “worm-like” capability.
What to Look for (Indicators)
If you are a developer, SOC analyst, or DevOps person, here are signs to watch out for:

Unexpected versions of dependencies in package.json/ package-lock.json/ npm audit warnings.
Post-install / lifecycle scripts in package.json that you don’t recognize.
Unfamiliar GitHub Actions workflows appearing in your repositories.
Repos which are created with the name “Shai-Hulud” or -migration suffix, especially if private → public.
Exfiltration endpoints / public GitHub repos with names matching “Shai-Hulud.”
Secrets that appear in environment variables or developer machines show tokens like GITHUB_TOKEN, NPM_TOKEN, and cloud keys.
Mitigation & What Defenders Should Do

Rotate all potentially compromised secrets/tokens (GitHub, npm, cloud keys).
Remove or rollback malicious package versions. Clean npm cache.
Audit all repos for unauthorized workflows, especially GitHub Actions. Remove suspicious workflows.
Only give publishing rights to well-trusted maintainers. Use multi-factor authentication (2FA) on npm & GitHub.
Monitor CI/CD logs for unusual patterns: external calls during build, adding new workflows, and unexpected repository visibility changes.
My Take
This incident highlights how attackers increasingly target the trust ecosystem rather than the code itself. Supply chain compromises like this show that protecting software development pipelines, developer credentials, and package registries is as critical as defending production systems.
