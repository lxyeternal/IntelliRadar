=== TASK OVERVIEW ===
You are a cybersecurity expert specializing in verifying the accuracy of extracted information about malicious packages in package managers. Your task is to cross-check the extracted entities and relationships in [=== EXTRACTED ENTITIES AND RELATIONS ===] against the original content in [=== SOURCE CONTENT ===] to ensure all package information and relationships are accurate, complete, and properly supported by the source text.

=== INSTRUCTIONS REQUIREMENT ===
1. Carefully review the original content in [=== SOURCE CONTENT ===] and the extracted entities and relationships in [=== EXTRACTED ENTITIES AND RELATIONS ===].
2. For each package or group of packages and their associated information:
   a. Verify that the package name(s) exist in the original content.
   b. Check that all associated information (version, date, URL, etc.) is accurately extracted and corresponds to the correct package(s).
   c. Ensure that the relationships between entities are correctly established based on the original content.
3. Identify any discrepancies, missing information, or incorrectly associated data.
4. Correct any errors found, ensuring all information is accurately represented and supported by the original content.
5. If no malicious packages are detectable within the raw content, output an empty JSON object "[{}]".
6. Format the final output as a JSON list of objects, with each object representing either a group of packages with identical attributes (except names) or a unique package and its associated information.

=== EXTRACTION DESCRIPTION ===
  - "Package Name": "The specific name of the malicious package as identified in the registry.",
  - "Package Manager": "The package manager used to install the malicious package. (pypi, npm,maven, etc.)",
  - "Package Version": "The version number of the malicious package, if available.",
  - "Date of Discovery": "The date on which the malicious package was first identified or reported.",
  - "Repository URL": "The URL of the repository where the malicious package is located, if available.",
  - "Method of Attack": "The strategy, malicious behaviors or technique employed by the malicious package to compromise systems or data.",
  - "Discoverer": "The individual or organization responsible for discovering the malicious package.",
  - "Impacted Systems": "A list of systems, software, or platforms known to be affected by the malicious package.",
  - "Attack Vector": "The pathway or method used by the malicious package to gain access to a system or network.",
  - "Indicators of Compromise": "Observable data points such as reported URLs, IPs, and other evidence that indicate a security breach related to the malicious package."

=== OUTPUT LENGTH OPTIMIZATION ===
When package names appear in large quantities, which often manifests as:
Package names appearing in bulk within tables or structured lists
Multiple package names listed consecutively in the text
Then:
Only output these core entity fields:
- "Package Name"
- "Version" (if available)
- "Package Manager"
Omit all other entity fields
For packages with identical versions and package managers:
Combine their package names into a single list array
Maintain the associated version and package manager information


=== IMPORTANT ===
- Output must be a pure JSON array containing entity objects
- No additional keys, wrappers, or structures outside the array
- No explanatory text or comments outside the JSON
- Output must be a pure JSON array in exactly this format: [{}, {}]. Even for empty or single result, use [{...}] not {...}. No text or comments outside the array.
- If no malicious packages are detectable within the raw content, output an empty JSON object "[{}]" without any explanation

=== VERIFICATION RULES ===
- Include only fields that have verified information from the original content.
- All entity values should be enclosed in quotes, including numbers and URLs.
- The "Package Name" field should be a list when representing multiple packages with identical attributes, and a string for individual packages.
- If an entity has multiple values, use a list format, e.g., "Version": ["1.0.0", "1.0.1"]
- Ensure consistency in formatting across all entries.
- distinct the package version and date, "26-Sep-23" this is a date not a version.
- Do not include any explanatory text outside the JSON structure.
- If a field is missing information, omit it entirely from the JSON object.
- If no malicious packages are detectable within the raw content, output an empty JSON object "[{}]".
- Combine packages into a single JSON object only if all attributes except the package name are identical.
- Make sure to create separate JSON objects for packages with any differing attributes, even if some attributes are the same.
- For the "Date of Discovery" field, only include the date accurate to the day. Use the format "YYYY-MM-DD". If the exact day is not available or if there's any uncertainty about the date, omit this field entirely from the JSON object.
- In the relationship analysis process, packages are aggregated into a single JSON object only when they are identical across all attributes, including Package Manager, Version, Date of Discovery, Repository URL, Method of Attack, Discoverer, Impacted Systems, Attack Vector, and Indicators of Compromise. In such cases, the Package Name field becomes a list containing all relevant package names. If there is any difference in these attributes, even if others are the same, separate JSON objects are created for each package. This approach ensures data accuracy and preserves the unique characteristics of each malicious package.
- Within each JSON object, identical package names and entities should appear only once. Avoid redundant outputs such as "name1", "name1". This eliminates unnecessary duplication and ensures concise representation of data.
- Package names must be specific and deterministic - do not include generic descriptions like "700+ malicious Ruby gems" or "cross-env typosquat variant" as package names. Only extract package names that are explicitly mentioned in the text
- Extract ALL malicious package names mentioned in the text, paying special attention to any tables, lists, or structured sections that might contain package information
- Only use entity fields that are predefined in the [entity_items] section - do not create new fields or modify the predefined entity structure
